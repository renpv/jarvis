# Pesquisa: Chatwoot self-hosted (Docker, canais Meta, Caddy)

Data de acesso: 2026-10-30. Todas as fontes foram lidas nesta data.

## Resumo prático

- Versão estável com pelo menos 14 dias: **v4.18.0** (publicada em 2026-09-18). As v4.19.0 (2026-10-20) e v4.19.1 (2026-10-24) são mais novas que 14 dias [F1][F2].
- O compose oficial usa `chatwoot/chatwoot:latest` (fixe a tag), `pgvector/pgvector:pg16` e `redis:alpine`, com serviços `rails` e `sidekiq` [F3].
- Preparo do banco: `docker compose run --rm rails bundle exec rails db:chatwoot_prepare` [F4].
- Em produção só precisam estar certos SECRET_KEY_BASE, FRONTEND_URL, POSTGRES_PASSWORD, REDIS_PASSWORD, RAILS_ENV=production, FORCE_SSL=true e ENABLE_ACCOUNT_SIGNUP=false [F5].
- Caddy: **não use `auto_https off` global** (desliga certificados também). Use `bind` por site: sites da VPN com `http://` + `bind 10.8.0.1`, e o site público com `bind <IP público>`. Testei com Caddy 2.11.7 (ver seção 8).

## 2. Compose de produção oficial (branch develop, lido em 2026-10-30) [F3]

- Não verifiquei se o arquivo na tag v4.18.0 é idêntico ao da `develop`.
- `base` (âncora): imagem `chatwoot/chatwoot:latest`, `env_file: .env`, volume `storage_data:/app/storage`.
- `rails`: `depends_on` postgres e redis; porta `127.0.0.1:3000:3000`; env `NODE_ENV=production`, `RAILS_ENV=production`, `INSTALLATION_ENV=docker`; `entrypoint: docker/entrypoints/rails.sh`; `command: ['bundle','exec','rails','s','-p','3000','-b','0.0.0.0']`; `restart: always`.
- `sidekiq`: mesmas variáveis de ambiente; `command: ['bundle','exec','sidekiq','-C','config/sidekiq.yml']`; sem entrypoint próprio.
- `postgres`: imagem **`pgvector/pgvector:pg16`** (o compose oficial já usa pgvector; o Chatwoot usa a extensão para recursos de IA/busca); volume `postgres_data`; env `POSTGRES_DB=chatwoot`, `POSTGRES_USER=postgres`, `POSTGRES_PASSWORD=` (você define); porta `127.0.0.1:5432`.
- `redis`: imagem **`redis:alpine`** (sem versão fixa); `command: sh -c 'redis-server --requirepass "$REDIS_PASSWORD"'`; `env_file: .env`; volume `redis_data`; porta `127.0.0.1:6379`.
- Volumes: `storage_data`, `postgres_data`, `redis_data`.
- O entrypoint `rails.sh` remove `server.pid`, limpa `tmp/cache`, espera o Postgres (`pg_isready`), roda `bundle install`/`bundle check` e faz `exec "$@"` [F6].
- Preparo/migração (primeira instalação e a cada atualização de imagem): `docker compose run --rm rails bundle exec rails db:chatwoot_prepare`. A doc avisa que `rails db:migrate` no primeiro setup pode dar erro. Depois `docker compose up -d`. Teste: `curl -I localhost:3000/api` deve dar 200. A doc manda colocar um proxy reverso na frente, pois os containers escutam só em localhost [F4].
- Requisitos: Docker 20.10.10 e Compose v2.14.1 [F4].

## 3. Variáveis de ambiente

Base: `.env.example` da develop [F5] e doc de variáveis [F7].

Obrigatórias em produção:
- `SECRET_KEY_BASE`: alfanumérica, sem símbolos; gerar com `rake secret` [F5][F7].
- `FRONTEND_URL`: URL pública, ex. `https://chat.seudominio.tld` [F7].
- `POSTGRES_HOST=postgres`, `POSTGRES_USERNAME=postgres`, `POSTGRES_PASSWORD=...` (igual ao do serviço postgres do compose). `POSTGRES_DATABASE` pode ficar vazio (nome padrão) [F5][F4].
- `REDIS_URL=redis://redis:6379` e `REDIS_PASSWORD=...` (o mesmo valor é usado pelo `--requirepass`) [F5][F3].
- `RAILS_ENV=production` (o `.env.example` traz `development`; o compose já define `RAILS_ENV=production` nos serviços rails e sidekiq) [F5][F3].

Recomendadas:
- `ENABLE_ACCOUNT_SIGNUP=false` (no `.env.example` já é `false`; `true` permite cadastro público; `api_only` desliga só a UI) [F5].
- `FORCE_SSL=true` quando o proxy entrega HTTPS (padrão `false`) [F5]. A doc de variáveis não descreve FORCE_SSL [F7].
- `RAILS_LOG_TO_STDOUT=true` e `LOG_LEVEL=info` (já assim no `.env.example`) [F5].
- `ACTIVE_STORAGE_SERVICE=local` (padrão; arquivos em `/app/storage`). A doc recomenda nuvem (S3 etc.) para evitar perda de dados [F5][F7].
- E-mail (opcional, mas sem ele não há convite/recuperação de senha): `MAILER_SENDER_EMAIL`, `SMTP_ADDRESS`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_DOMAIN`, `SMTP_AUTHENTICATION`, `SMTP_ENABLE_STARTTLS_AUTO`. Se `SMTP_ADDRESS` vazio, tenta sendmail [F5].
- Ajuste de desempenho: `RAILS_MAX_THREADS=5`, `WEB_CONCURRENCY` (comentada) [F5].
- Rate limit: `ENABLE_RACK_ATTACK` e variantes `..._WIDGET_*` aparecem comentadas no `.env.example` (não li a descrição completa) [F5].

## 4. Requisitos de CPU e memória [F8]

- 4 CPUs e 4 GB de RAM atendem até 10.000 conversas por dia; 8 CPUs e 8 GB até 20.000.
- Recomenda-se pelo menos 1 GB de swap para não faltar memória nas atualizações.
- Postgres: pelo menos 5-10 GB de disco. Redis: a partir de 100 MB. Sidekiq pode passar de 1 GB em servidor muito ativo.
- Disco do app depende dos anexos; a doc sugere object storage compatível com S3.
- Para uso pequeno não achei número oficial menor; os 4 GB são "obrigatório" na doc.

## 5. Canais

### WhatsApp
- Opções na doc de ajuda: **WhatsApp Cloud (Meta)** com "Quick setup" (embedded signup) ou **fluxo manual**; **Twilio** (guia próprio). A página lida não menciona 360dialog [F9]. O `routes.rb` tem rota de Twilio (`namespace :twilio`) [F10]. Não confirmei na documentação se 360dialog segue suportado nesta versão.
- Fluxo manual: criar o inbox em Settings > Inboxes > WhatsApp > WhatsApp Cloud > manual; informar Phone Number ID, WhatsApp Business Account ID e token permanente de usuário de sistema (expiração "Never", permissões `whatsapp_business_management` e `whatsapp_business_messaging`). O Chatwoot verifica e configura o webhook no Meta sozinho; se falhar, copiar "Webhook URL" e "Webhook Verification Token" da tela e colar em Meta > WhatsApp > Configuration > Verify and save, e assinar o campo `messages` [F9].
- Formato da URL (código): `GET/POST {FRONTEND_URL}/webhooks/whatsapp/:phone_number` (GET faz o `verify`, POST recebe eventos). O verify token é gerado por inbox (`ensure_webhook_verify_token`) [F10][F11].
- Servidor precisa de URL pública HTTPS alcançável pelo Meta (exigência da Meta; a doc do Chatwoot lida não detalha). Coexistência com o app WhatsApp Business não é suportada [F9].

### Facebook Messenger [F12]
- Variáveis: `FB_APP_ID`, `FB_APP_SECRET`, `FB_VERIFY_TOKEN` (string aleatória sua).
- Webhook (callback): `{FRONTEND_URL}/bot`; verify token = `FB_VERIFY_TOKEN`.
- App Meta tipo Business, produtos Facebook Login (Web OAuth Login e JS SDK, com o domínio do Chatwoot) e Messenger; domínio do Chatwoot em "App domains". Assinaturas: `messages`, `messaging_postbacks`, `message_deliveries`, `message_reads`, `message_echoes`.

### Instagram [F13]
- Variáveis: `IG_VERIFY_TOKEN`, `FB_APP_ID`, `FB_APP_SECRET`.
- Webhook: `{FRONTEND_URL}/webhooks/instagram`; verify token = `IG_VERIFY_TOKEN`.
- Requer página do Facebook ligada a conta profissional do Instagram. Para produção, a app precisa de revisão da Meta (advanced access a `instagram_manage_messages`, `instagram_basic`, `pages_show_list`, `pages_manage_metadata`, `pages_messaging`, `business_management`).
- A página da doc diz que esse fluxo (Facebook Login) deixa de ser suportado a partir da v4.1 e recomenda o "Instagram Business Login". As variáveis desse novo fluxo não constam na página que li; o `.env.example` só lista as acima [F5][F13]. Em aberto.

## 6. Docker rootless

- Não há nada específico do Chatwoot sobre rootless na doc oficial nem encontrei issue documentando problema (busca feita; sem resultado relevante).
- O Dockerfile da develop não define `USER` nem `chown`: o processo roda como root dentro do container [F14]. No rootless, root do container mapeia para o seu usuário no host, então volumes nomeados (`storage_data` etc.) funcionam sem acerto de UID. Bind mounts de pastas do host podem exigir ajuste de dono via faixa subuid (inferência; a doc do Docker não tem seção sobre bind mounts) [F15].
- Limitações documentadas do Docker rootless [F15][F16]: `/etc/subuid` e `/etc/subgid` com pelo menos 65.536 IDs (senão erro `lchown` no pull); portas abaixo de 1024 não podem ser publicadas (`net.ipv4.ip_unprivileged_port_start=0` ou `CAP_NET_BIND_SERVICE` no rootlesskit); IP de origem do cliente não é preservado por padrão (com RootlessKit 3.0+, `"userland-proxy": false` no `daemon.json`); `data-root` em NFS não funciona. O compose do Chatwoot publica só em `127.0.0.1:3000/5432/6379` (portas altas), sem problema.
- Se o Caddy também rodar em container rootless e precisar de 80/443, vale a regra de portas privilegiadas acima.

## 7. Backup [F17]

- Banco: `pg_dump`. Exemplo oficial: `pg_dump -U postgres -W -F t chatwoot_production > backup.tar`. Neste compose o banco se chama `chatwoot` (POSTGRES_DB), então adapte o nome. Via Docker: `docker compose exec postgres pg_dump -U postgres -F c chatwoot > chatwoot.dump` (adaptação minha).
- Arquivos: com storage local, copiar a pasta `storage` (no compose, o volume `storage_data` montado em `/app/storage`). Com S3/GCS, usar o backup do provedor.
- Guardar fora do servidor e com acesso restrito; frequência conforme o quanto de dado você aceita perder.

## 8. Caddy v2: sites só na VPN (http) + um site público com HTTPS

Fatos documentados:
- `auto_https off` "desabilita tanto a automação de certificados quanto os redirects HTTP-para-HTTPS". Global, vale para todos, inclusive o site público [F18]. Alternativas: `disable_redirects` (só redirect), `disable_certs`, `ignore_loaded_certs` [F18].
- `auto_https off` não faz o site servir em HTTP; para isso use prefixo `http://` ou sufixo `:80` no endereço [F18].
- HTTPS automático não é ativado para site com `http://`, nem para servidor que escuta só a porta HTTP [F19].
- `default_bind` vale para todos os sites sem `bind`; só se aplica a servidores gerados pelo Caddyfile; o servidor de redirect HTTP->HTTPS automático "não herda" esses endereços; contorno: declarar um site `http://` (pode ser vazio) [F18]. `bind` de site sobrepõe `default_bind` [F18][F20].
- HTTP-01 exige porta 80 acessível de fora; TLS-ALPN exige 443; DNS-01 não exige portas [F19].

Testes que fiz (Caddy 2.11.7, imagem `caddy:2`, `caddy adapt` e execução com rede host em IPs 127.0.0.x e portas 8080/8443):
- Com `default_bind 10.8.0.1` global + site público com `bind <IP público>`: o `adapt` põe `"bind_host": "10.8.0.1"` nos issuers ACME do site público (em `challenges`). Isso pode atrapalhar o desafio HTTP-01 pela interface errada. Não testei emissão real (sem domínio). Evite `default_bind` nesse caso.
- Com `bind` explícito em cada site (sem `default_bind`, sem `auto_https off`): o `adapt` não gera `bind_host` nos issuers; na execução, o site `http://` com bind escutou só no IP da VPN (127.0.0.2 no teste), o site público escutou no IP dele (443) e o redirect HTTP->HTTPS também ficou preso ao IP do site público (porta 80), sem conflito entre os dois.

Config recomendada (testada só até o nível de `adapt` e escuta de portas; certificado Let's Encrypt real não foi emitido):

```
{
	email voce@dominio.tld
}

# VPN, só HTTP
http://painel.interno {
	bind 10.8.0.1
	reverse_proxy 127.0.0.1:8080
}

# Público, HTTPS automático (Let's Encrypt), escutando só no IP público
chat.dominio.tld {
	bind 203.0.113.10
	reverse_proxy 127.0.0.1:3000
}
```

Pré-requisitos: DNS A/AAAA do domínio para o IP público, portas 80 e 443 abertas, diretório de dados do Caddy persistente [F19]. Para o Chatwoot atrás do Caddy: `FRONTEND_URL=https://chat.dominio.tld` e `FORCE_SSL=true`.
